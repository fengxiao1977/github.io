In-place upgrade of a legacy operating system

An in-place upgrade advances the operating system that is already installed on an instance. The application stays where it is. A new machine is not built, and the workload is not migrated onto it.

What an in-place upgrade is

The version change is done with the upgrade programs supplied by the operating-system vendor, wrapped in automation so the same sequence can be repeated on the instances you select. Microsoft, Red Hat, and Oracle each publish a supported way to move from an older major release to a newer one. Automation coordinates those vendor tools; it does not replace them.

That is a different job from a migration. A migration stands up another instance, installs the application there, and cuts traffic over. An in-place upgrade keeps the same instance and changes the OS underneath the software that is already present.

When it is useful

The approach suits older applications that cannot be installed a second time. Typical cases are lost source code, or an independent software vendor that has gone out of business, so there is no installer and no vendor left to rebuild the stack on a fresh image.

It also shrinks the window of exposure that comes with an unpatched older operating system. Releases that no longer receive security fixes leave known flaws in place. Moving the instance onto a supported release reduces that exposure without asking the application to be reinstalled.

Supported paths

These are the in-place routes described for this offering:

  • Windows Server 2012 R2 → Windows Server 2016 and later
  • Windows Server 2016 → Windows Server 2022 and later
  • Red Hat Enterprise Linux 7 → Red Hat Enterprise Linux 8
  • Red Hat Enterprise Linux 8 → Red Hat Enterprise Linux 9
  • Oracle Linux 7 → Oracle Linux 8

Rollback

If an upgrade fails, it can be rolled back. The instance is returned to the state it was in before the upgrade started.

How this is requested and billed in AMS Operations on Demand

Inside AWS Managed Services, this upgrade is one item in the Operations on Demand catalog. After the engagement is scoped, it is started with a service request. There is no separate long-term contract just for this item.

Time is sold in monthly blocks of 20 hours. At least one block is billed every month the engagement is active, even if fewer than 20 hours are used. Hours left unused in a month do not carry into the next month. An extra allocated block that is not used at all is not billed.
